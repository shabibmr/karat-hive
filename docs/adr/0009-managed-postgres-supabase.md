# Managed PostgreSQL on Supabase, with the bundled Data API disabled

PostgreSQL is a **managed Supabase instance** (project `husuemlfcvacrysapwho`, region `ap-northeast-2`, Postgres 17) for local development, CI-adjacent manual testing, demo, and the checkpoint verticals. The backend connects **directly** on the Postgres wire protocol as the `postgres` role via `DATABASE_URL` — it does **not** use any of Supabase's bundled application services. This fills the gap left open by `adr/0007` (which fixes "Node.js monolith over PostgreSQL" but not who operates the database) and supersedes the parenthetical in `adr/0008` that assumed a self-managed database.

**Why.** For an MVP with no infrastructure team, a managed Postgres removes backup/PITR, patching, and connection-tooling toil for zero cost on the free tier, and Supabase gives a SQL console + MCP tooling that made schema bring-up fast. `adr/0007`'s invariants are untouched: it is still one Node deployable, still one PostgreSQL system of record, still `pg_trgm` for search and a transactional outbox for async — Supabase is a host, not an architecture change.

**The Data API must be off.** Supabase auto-exposes every `public` table through PostgREST to the `anon` key, which is a public credential. That directly breaks the masking pipeline (`Architecture-Backend.md` §9, `FR-SYS-003`, `NFR-013`, `BR-006`): masked identity fields are absent from API payloads *because the backend omits them*, and an open Data API lets any client read the underlying rows and bypass that entirely. It also breaks the ownership rule (`Architecture-Backend.md` §12.1) that the monolith is the only database client. Lockdown, applied 6 September 2026 as Supabase migration `lock_down_data_api_public_schema`:

- `ENABLE ROW LEVEL SECURITY` on all `public` tables, **no policies** → deny-all.
- `REVOKE ALL` on all `public` tables and sequences, and `REVOKE USAGE ON SCHEMA public`, from `anon` and `authenticated`.
- `ALTER DEFAULT PRIVILEGES FOR ROLE postgres … REVOKE ALL … FROM anon, authenticated` so future Prisma migrations (which run as `postgres`) cannot silently re-expose new tables.

Safe for the backend because it connects as `postgres`, which **owns** every table (Prisma migrates as `postgres`) and has `rolbypassrls = true`; `service_role` (server-only, never shipped to a client) also has `rolbypassrls`. Verified: `SET ROLE anon` → every read denied; backend `/ready` = 200, `prisma migrate status` = up to date, a live write through the API into an RLS-enabled table succeeded. Optional further hardening — turning the Data API off at the project level (Dashboard → Project Settings → API) — is not required, since `anon` now has no reachable privilege.

**Consequences.**
- Supabase Auth (GoTrue), Realtime, and Edge Functions are unused. Authentication is the backend's own JWT (`Architecture-Backend.md` §14); do not introduce a second identity system.
- Storage stays on **Cloudflare R2 / MinIO** (`adr/0008`) — this decision does not move object storage onto Supabase Storage. (The KYC `kyc` bucket that currently lives in this Supabase project is a checkpoint-1 convenience noted in `docs/checkpoints/`, not the production target.)
- Region `ap-northeast-2` (Seoul) is **not** UAE-resident. Acceptable for non-production, which holds only synthetic data. Production database residency is part of the open "cloud provider and region" infrastructure item in `Architecture-Backend.md` §22.1 — resolved by either a UAE-region managed provider (e.g. Supabase does not currently offer one; AWS RDS/Aurora `me-central-1` does) or a documented legal basis.
- Two migration ledgers coexist: Prisma's `_prisma_migrations` is authoritative for schema; the Supabase migration log holds only out-of-band changes (Storage bucket creation, the partial-index catch-up, this lockdown). Keep schema in Prisma; use Supabase migrations only for provider-level state.

**Considered options.** **Self-managed PostgreSQL** on the eventual cloud provider (the original `adr/0008` assumption) — no third-party data processor, full residency control, but needs the ops capability the MVP does not have yet; remains the likely production shape. **AWS RDS/Aurora `me-central-1`** — managed *and* UAE-resident, the strongest production candidate, but not free and heavier to stand up for day-to-day development. **Neon** — managed Postgres with branching, generous free tier, no bundled anon API to lock down, but no UAE region and no advantage over Supabase for this phase. **Supabase with the Data API left on and secured by real RLS policies** — rejected: writing and maintaining a full policy set for 42 tables duplicates the authorization logic that already lives in the backend (`Architecture-Backend.md` §14.4), for an access path nothing uses.
